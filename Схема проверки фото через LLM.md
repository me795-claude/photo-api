# Схема проверки фото на пропуск через LLM (Open WebUI)

Основа: документ «Требование к фото на пропуск.docx» (9 требований, у каждого есть картинка с примерами «подходит / не подходит») и API Open WebUI (`/api/chat/completions`, совместимый с OpenAI).

## 1. Что проверяем: требования → `test_type`

| # | `test_type` | Требование из документа | Когда `failed` |
|---|---|---|---|
| 1 | `format` | 35×45 мм, от подбородка до макушки 32–36 мм; в цифре главное — пропорции | соотношение сторон ≠ 7:9 (±3 %), голова занимает меньше 71 % или больше 80 % высоты кадра, голова обрезана |
| 2 | `quality` | Снимок чёткий, без сгибов и пятен | размытие, шум, пиксели от сжатия, сгибы, пятна, блики на отсканированном фото |
| 3 | `lighting_color` | Цветное, без теней, пересвета и затемнения | ч/б или сепия, тени на лице или фоне, пересвеченные или слишком тёмные участки |
| 4 | `background` | Фон однотонный | узор, предметы, градиент, другие люди, заметные тени на фоне |
| 5 | `headwear` | Головной убор недопустим | шапка, кепка, капюшон, платок, повязка и т. п. |
| 6 | `head_position` | Голова прямо, лицом к камере, без поворотов | поворот, наклон, запрокидывание головы |
| 7 | `gaze_expression` | Смотреть в объектив, лицо нейтральное, рот закрыт | взгляд в сторону, улыбка, открытый рот, гримаса |
| 8 | `face_eyes` | Лицо видно полностью, глаза открыты | лицо закрыто волосами, рукой или предметом; глаза закрыты или прищурены |
| 9 | `glasses` | Очки можно, если оправа тонкая, не закрывает глаза, стёкла прозрачные и без бликов | тёмные или тонированные стёкла, блики, толстая оправа на линии глаз. **Нет очков → `successed`** |

## 2. Схема взаимодействия

```mermaid
sequenceDiagram
    participant C as Клиент (форма загрузки)
    participant S as Photo-API (бэкенд)
    participant L as Open WebUI → qwen3.8-flash-next

    C->>S: POST /photo/check (jpeg/png)
    S->>S: 0. Предобработка: декодирование, поворот по EXIF,<br/>уменьшение до 1024 px по длинной стороне, JPEG q=90
    S->>S: 1. Проверки кодом: пропорции 7:9, цвет/ч-б,<br/>гистограмма яркости, резкость (дисперсия лапласиана)
    S->>L: 2. POST /api/chat/completions<br/>system: требования + правила ответа<br/>user: текст + image_url (data:image/jpeg;base64)<br/>temperature=0, response_format=json_schema
    L-->>S: JSON {checks:[...9 объектов...]}
    S->>S: 3. Проверка по схеме: 9 test_type, каждый ровно один раз<br/>ошибка → 1 повтор с текстом ошибки
    S->>S: 4. Слияние: результат кода AND результат LLM<br/>(format, lighting_color, quality)
    S-->>C: {checks:[...], overall}
```

### Почему часть проверок делает код, а не LLM
Языковые модели плохо **измеряют** (миллиметры, проценты, пропорции), зато хорошо **распознают** (очки, улыбка, головной убор). Поэтому:
- **Только код:** соотношение сторон 35:45; цветное ли фото (средняя насыщенность HSV больше порога).
- **Код + LLM, итог через AND** (`failed`, если не прошёл хоть один): пересвет и затемнение (доля пикселей у 0 и 255), резкость (дисперсия лапласиана), высота головы (точно её считает детектор лицевых точек, например MediaPipe; без него — только оценка LLM).
- **Только LLM:** `background`, `headwear`, `head_position`, `gaze_expression`, `face_eyes`, `glasses`.

## 3. Запрос к LLM

`POST {OPENWEBUI_URL}/api/chat/completions`
Заголовки: `Authorization: Bearer sk-...`, `Content-Type: application/json`

```json
{
  "model": "qwen3.8-flash-next",
  "stream": false,
  "temperature": 0,
  "seed": 42,
  "max_tokens": 1500,
  "messages": [
    { "role": "system", "content": "<SYSTEM_PROMPT, раздел 4>" },
    { "role": "user", "content": [
        { "type": "text", "text": "Проверь фото на пропуск по всем 9 пунктам. Верни только JSON." },
        { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,/9j/4AAQ..." } }
    ]}
  ],
  "response_format": {
    "type": "json_schema",
    "json_schema": { "name": "photo_check", "strict": true, "schema": "<JSON Schema, раздел 5>" }
  }
}
```

Фото передаётся **прямо в сообщении** (base64). Загружать его через `/api/v1/files/` не нужно: этот путь отправляет файл в RAG (извлечение текста), и модель не увидит само изображение.

## 4. System prompt

```text
Ты — система контроля фотографий на пропуск. Оцени изображение строго по 9 пунктам и верни JSON.

Пункты (test_type → критерий):
1. format — портретный кадр с пропорциями 35×45; голова от подбородка до макушки (без волос)
   занимает 71–80% высоты кадра; голова не обрезана, по центру.
2. quality — снимок чёткий, без размытия, шума, артефактов сжатия, сгибов, пятен.
3. lighting_color — фото цветное; нет теней на лице и фоне, нет пересвета и затемнения.
4. background — фон однотонный, без узоров, предметов, людей и градиента.
5. headwear — нет головного убора (шапка, кепка, капюшон, платок, повязка и т.п.).
6. head_position — голова прямо, лицом к камере, без поворота и наклона.
7. gaze_expression — взгляд в объектив, выражение нейтральное, рот закрыт, нет улыбки.
8. face_eyes — лицо видно полностью (не закрыто волосами, руками, предметами), оба глаза открыты.
9. glasses — если очков нет → successed. Если есть: оправа тонкая и не закрывает глаза,
   стёкла прозрачные, без бликов и тонировки; иначе failed.

Правила:
- Верни ровно 9 объектов, по одному на каждый test_type, в указанном порядке.
- result: только "successed" или "failed".
- comment: при failed — кратко и конкретно по-русски, что не так и как исправить
  (например: "Тёмные стёкла очков закрывают глаза — снимите очки или замените на прозрачные").
  При successed — пустая строка "".
- Если по пункту нельзя уверенно судить (плохо видно, лица нет) — failed с объяснением.
- Если на фото нет человека или больше одного — все пункты failed с этим комментарием.
- Только JSON, без пояснений и markdown.
```

## 5. JSON Schema ответа

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["checks"],
  "properties": {
    "checks": {
      "type": "array",
      "minItems": 9,
      "maxItems": 9,
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["test_type", "result", "comment"],
        "properties": {
          "test_type": { "type": "string", "enum": ["format","quality","lighting_color","background","headwear","head_position","gaze_expression","face_eyes","glasses"] },
          "result":    { "type": "string", "enum": ["successed","failed"] },
          "comment":   { "type": "string" }
        }
      }
    }
  }
}
```

Пример ответа (для фото с тёмными очками из документа):

```json
{
  "checks": [
    { "test_type": "format",          "result": "successed", "comment": "" },
    { "test_type": "quality",         "result": "successed", "comment": "" },
    { "test_type": "lighting_color",  "result": "successed", "comment": "" },
    { "test_type": "background",      "result": "successed", "comment": "" },
    { "test_type": "headwear",        "result": "successed", "comment": "" },
    { "test_type": "head_position",   "result": "successed", "comment": "" },
    { "test_type": "gaze_expression", "result": "failed",    "comment": "Направление взгляда не видно за тёмными очками" },
    { "test_type": "face_eyes",       "result": "failed",    "comment": "Глаза закрыты тёмными стёклами очков" },
    { "test_type": "glasses",         "result": "failed",    "comment": "Тонированные стёкла — снимите очки или замените на прозрачные" }
  ]
}
```

Бэкенд добавляет поле `overall` (`successed`, только если все 9 пунктов `successed`) и может добавить служебные поля (`model`, `latency_ms`). Ответ модели этих полей не содержит.

## 6. Надёжность ответа

1. **Проверка ответа:** разобрать JSON, сверить со схемой, проверить, что все 9 `test_type` есть и не повторяются.
2. **Повтор:** при ошибке отправить запрос ещё раз и добавить сообщение `"Ответ не соответствует схеме: <ошибка>. Верни исправленный JSON."` Не больше 1–2 повторов.
3. **Если повторы не помогли:** сервис отвечает `503` / `"status": "llm_unavailable"`. Нельзя молча ставить `successed`.
4. **Если `json_schema` не поддерживается** (зависит от бэкенда модели): `response_format: {"type":"json_object"}`, а для Ollama-моделей — `"format": <schema>` в `/ollama/api/chat`. Проверка из п. 1 остаётся в любом случае.
5. **Блок размышлений:** если модель возвращает `<think>…</think>`, вырезать его до разбора JSON или отключить reasoning в параметрах модели.

## 7. Роль `pplx-embed-v1-4b` и `nemotron-rerank-1b-v`

Обе модели работают **с текстом** и в проверке изображения не участвуют. Требования (9 пунктов) целиком помещаются в system prompt, поэтому RAG не нужен. Где они могут пригодиться дальше:
- **Нормализация комментариев:** через эмбеддинги свести свободные `comment` к справочнику типовых причин отказа (статистика, единые подсказки для пользователя).
- **Поиск похожих отказов и регламентов:** если появится база внутренних инструкций или обращений, `embed` → поиск, затем `rerank` → лучшие фрагменты для оператора.

## 8. Что проверить до разработки

- [ ] У `qwen3.8-flash-next` в Open WebUI включена возможность **Vision** (Admin → Models → Capabilities). Без неё изображение не дойдёт до модели. Это главный риск: на странице API передача `image_url` прямо не описана, хотя формат совместим с OpenAI.
- [ ] Модель поддерживает `response_format: json_schema`. Если нет — запасной вариант из п. 6.4.
- [ ] API-ключи включены администратором, у пользователя сервиса есть разрешение «API Keys».
- [ ] Включён ли у администратора «Stream Chat Response»: он может включить потоковую выдачу даже при `stream:false`, тогда клиент должен собирать SSE.
- [ ] **Набор для калибровки:** 11 картинок из документа (по 2 «не подходит» + 1 «подходит» на требование) нарезать на отдельные фото и сделать регрессионным тестом. По нему подобрать формулировки промпта и пороги для проверок кодом.
